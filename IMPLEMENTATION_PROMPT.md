# Implementation prompt - Implement an audit's repair packages

For work between audit and re-audit: an orchestrating agent implements the packages from `tasks/` of a closed run, wave by wave, then hands over to the re-audit (`RESUME_PROMPT.md`, Variant B). The audit itself never changes the product; this assignment provides the separate authorization for that work.

First adjust the package path, scope (waves or package IDs) and integration line. In an agent that supports skills, explicitly invoke `production-readiness-audit implement` with that scope and integration rule.

```text
PACKAGE: ./production-readiness-audit

Implement repair packages from the latest closed audit run under ./audit-results/ (python -B "<PACKAGE>/tools/audit_tools.py" runs --project . lists the runs; if ambiguous, ask).

BASIS
In every new implementation session, read <PACKAGE>/MASTER_PROMPT.md completely in bounded chunks before continuing; it contains no security-check instructions. Then read run indexes, selected non-security REPORT.md sections (Executive summary, waves, HUMAN packages), audit.json records and selected task files. Do not load the whole audit.json into context. Task assignments are binding. After in-session compaction reread quick reference, current package sections, §10 and Appendix A.

Assignment files: this prompt, MASTER_PROMPT.md, tools/, SECURITY_REVIEW.md (audit: read only on reaching P8 after checkpoint verification; implementation: only sections 2 and 6 in the dedicated last wave/session), plus SKILL.md when invoked through the skill. Implementation does not run P0-P9 or SECURITY_REVIEW entry/closure procedures. Incompatible references require a new linked audit/re-audit, preserving artifacts; never change schema identifiers. Compatible differing prompt identifiers are warnings.

Initially skip security details in REPORT.md/audit.json and finding/task files. Use a neutral ID/category/reference/deferred-recheck index: audit-core/2 security items have category SECURITY; neutral indexes also treat legacy H as security; classification unknown applies only to runs without the field, never inferred from titles. Implement security packages in a dedicated last wave/session: only then read deferred finding/task/detail files and SECURITY_REVIEW sections 2 (safety) and 6 (reproduction/reporting), resolving unknown classifications. Their P8 checkpoint entry rule does not apply to authorized implementation. Dependent non-security packages wait for that wave. Resume implementation from IMPLEMENTATION.md and the current package with the same separation.

SCOPE AND AUTHORIZATIONS
- Packages: wave 1 [or: all waves in order | package IDs ...]. Do not implement HUMAN packages; ask me about open decisions together.
- Product changes are authorized only for these packages, each in its own branch and worktree outside my worktree.
- Integration into the main branch: only after my confirmation for each wave [or: after passed checks without asking]. No push, no deployment, no changes to remote targets.
- Other authorizations (network, environments, credentials) as in the audit run's starting assignment (RUN-STATE.json), unless I change them here.
- Protection rules as in the audit (master prompt §2), with one exception: branches, worktrees, commits on package branches and integration according to the rule above are authorized for these packages. The audit's workflow rules (§13 through §17, phases from P0) do not apply here. Restrictive project rules such as data classification or excluded providers apply; where rules conflict, the narrower rule applies. Project content goes to no additional provider without authorization, including implementers or reviewers. Secret values and personal data appear neither in commits, tests and outputs nor in IMPLEMENTATION.md; tests use synthetic values.

RULES
1. Establish the starting state. Compare it with the audit baseline: python -B "<PACKAGE>/tools/audit_tools.py" baseline --compare "<Run>/evidence/baseline/baseline-start.json". Do not commit, move or discard my uncommitted/new changes; ask. Reason: unrelated working states must not enter repair commits.
2. One package, one branch. Packages in a wave run in parallel only if their task files show that they share no files, contracts or data; otherwise run sequentially. At most 4 concurrent heavy processes across the entire run, including delegates and nested test workers; the orchestrator allocates this global budget and delegates do not multiply it.
3. Confirm first, then change. The implementer confirms the defect or hypothesis against the current state before making changes and reports deviations from the audited state. Diagnosis packages (INVESTIGATE) change no product code.
4. Regression tests. Carry over existing audit tests from evidence/audit-tests/. If a test must be adapted to changed code, its assertion remains equally strong; justify the adaptation. Each new or carried-over test fails against the old state at the intended assertion. A countercheck against the state before the package establishes this.
5. Run checks yourself. As orchestrator, run build, typecheck, tests and affected journeys on the package branch even when the implementer reports PASS. Reason: implementer environments may not support the required processes or containers. Resource-intensive verification runs sequentially unless a measured budget permits overlap. Before the last security wave/session, defer security-specific commands, subsets, scanners, output assessment and verdicts; inseparable suite results stay recorded for later assessment. Operational safety remains active. Label unstable tests; do not repeat until green. Use timeouts and stop resources you start.
6. Review the diff before integration. Changes stay within scope with no weakened tests, gates, error checks or secret values. Preserve line endings and encoding. For security, data integrity, payment or migration packages, an independent reviewer reviews the changes in their designated wave/session. The reviewer receives assignment, diff and test outputs, not the author's rationale. Reason: a separate inspection can find unsupported assumptions in consequential changes. Delegation briefs include allocated budget, provider/authorization limits, deferred-material restrictions and evidence format; only the orchestrator writes central status.
7. Keep status honest. An implemented package is candidate_complete, not fixed. Corrections run as another round of the same package with a reason. A finding is fixed only after the re-audit.
8. Record decisions. Immediately record my answers to HUMAN packages and open questions, and later authorizations, with date, exact wording, target and limits. The re-audit carries them over as dated user sources. Reason: decisions given only in chat are lost between sessions.
9. No bypasses. Without my consent, no --no-verify and no disabling hooks, gates or checking tools. Commits on my main branch occur only according to the integration rule above.
10. Progress. Maintain audit-results/<AuditRun>_implementation/IMPLEMENTATION.md: begin with this assignment verbatim, then record for each package its branch, rounds, checks run with results, review, integration state and open points, plus the "Decisions" section. Update it after each package so a new session can take over. Place no executable files there.
11. Context. Apply master prompt §16.2's session plan/budget method to implementation waves, recording boundaries and objective/scope/criterion/output in IMPLEMENTATION.md. Persist results and unresolved checks after packages. Without observable context usage, yield only at planned session boundaries; end the turn/run with an exact continuation instruction. Search before targeted reads; do not reread unchanged content still in context. A refusal/model-switch safe stop retains progress; no automatic provider/authorization change.

COMPLETION
After the selected scope: overall integration checks against the integrated state, meaning build, full suite and critical journeys; explicitly check interactions between packages. Then report to me the packages with status, open decisions and the re-audit command (RESUME_PROMPT.md, Variant B), preferably in a new session so the recheck does not build on implementation knowledge.
```
